### 3. OpenRouter response-cache confounder

The reference MUST add one bounded level-two section that identifies, but does not teach or recommend enabling, OpenRouter response caching:

- it is a separate gateway-response plane from provider prompt caching and can be enabled or disabled by `X-OpenRouter-Cache: true|false` or a preset `cache_enabled` setting; a preset `cache_enabled: false` cannot be overridden by the header, a request `X-OpenRouter-Cache: false` can disable a preset-enabled cache, `X-OpenRouter-Cache-TTL` overrides preset `cache_ttl_seconds`, and `X-OpenRouter-Cache-Clear` can force a refresh of the matching entry. Do not restate the response-cache default TTL in the reference in any unit: its volatile value also collides with the stale-sticky-claim guard, so direct auditors to the live response-caching page. Preset/header precedence must not be mistaken for provider prompt-cache behavior. Inspect these controls passively; sending a clear header against production traffic is an active intervention and is outside a passive audit;
- the docs do not state whether a response-cache HIT counts as the successful request that resets the sticky-session timer. Because a HIT is served before any provider is reached, require per-account verification before attributing a post-HIT provider miss or provider switch to sticky-routing failure;
- it is the `gateway_response` cache plane, is opt-in and off when neither a request header nor preset enables it, and its evidence includes `X-OpenRouter-Cache-Status`, `X-OpenRouter-Cache-Age` (HIT only), `X-OpenRouter-Cache-TTL` (remaining TTL on HIT, full TTL on MISS), and `X-OpenRouter-Cache-Source-Id` (HIT only); `X-OpenRouter-Cache-Status: MISS` is consistent with the response-cache plane being enabled on that traffic, an inference from the documented status behavior rather than a provider prompt-cache fact; corroborate it against request/preset configuration because the docs do not define these headers when the plane is disabled. Identical concurrent requests can both MISS and be billed independently, so concurrency-driven MISSes are not evidence that the plane is disabled; entries can also be evicted before TTL expiry under memory pressure, so MISS-heavy traffic inside the nominal TTL is not by itself evidence that the plane is disabled. Only successful `200 OK` responses are cached. `X-OpenRouter-Cache-TTL` is also a request control for a custom TTL expressed in seconds, documented in the range 1–86400 with out-of-range values clamped; the reference MUST distinguish request configuration from response evidence and omit the volatile default TTL entirely;
- its identity includes API key, model, endpoint type, streaming mode, and a normalized request-body SHA-256; extra whitespace is normalized away, while JSON property order and explicit-vs-omitted optional fields can produce different keys. Attribution headers such as `HTTP-Referer` and `X-Title`, and provider-specific headers, are not part of the cache key. Cache is scoped to an API key, and different API keys do not share cache even under the same account or organization. Therefore, a body-identical request from another tenant that reuses the same API key can replay the stored response despite differing `HTTP-Referer`, `X-Title`, or provider-specific headers; a shared API key shares a response-cache namespace only when the normalized body hash, model, endpoint type, streaming mode, and other documented key dimensions match. Review that conditional tenant isolation and provider-feature attribution explicitly against the existing `isolation` clinic dimension and AP-9b trust-boundary rule;
- a HIT returns zeroed billable usage and does not call the provider, so it MUST be partitioned out before prompt-cache ratio/accounting, latency/TTFT, and cost/ROI analysis and MUST NOT be counted as provider `cached_tokens` or provider warm-up. The reference MUST name the endpoint-specific zeroed fields: Chat Completions/Responses `prompt_tokens`, `completion_tokens`, and `total_tokens`; embeddings `prompt_tokens` and `total_tokens`; Anthropic Messages `input_tokens` and `output_tokens`. All-zero usage alone is not proof of a response-cache HIT: errors, empty records, endpoint-shape differences, and missing telemetry can produce zeroes, so require a cache-status/source signal or an explicitly verified endpoint contract. For streamed or body-only logs where response headers were not retained, use the documented `response_cache_source_id` from the generation record when available; otherwise report the plane as unresolved. A zero-input HIT contributes zero tokens, but it degrades the analyzer row and aggregate `denominator_status` to `ambiguous`; the aggregate is not decision-grade until the HIT is partitioned. The token-weighted value may remain numerically unchanged only after this status caveat is handled; malformed logs that retain nonzero cache details must not be treated as a HIT contract. Without partitioning, the result silently describes provider-reached records rather than end-to-end requests;
- analyzer behavior is shape-dependent and MUST be documented as such, not generalized as an OpenRouter fact: a raw OpenRouter-shaped record may select the analyzer's OpenAI/inclusive adapter and may already emit `denominator_status: valid`, while a wrapper-annotated `provider: "openrouter"` record remains ambiguous. Preserve the wrapper label in analyzer input and record the actual routed provider/model in the existing audit attribution dimensions (`route`/`model` or the keyed historical generation record); do not imply that the bundled analyzer supports an arbitrary additional attribution field. Treat the raw `valid` result as provisional until per-route inclusivity is verified. The reference MUST say that HIT partitioning and denominator interpretation are conditional on the route's verified usage semantics; the literal records and measured statuses belong only in the regression test, not in this bounded confounder section;
- response-cache TTL and ZDR behavior are diagnostic caveats: ZDR narrows the eligible provider/endpoint candidate set and can therefore remove cache-capable routes, but does not by itself prohibit provider implicit prompt caching because the ZDR page treats in-memory prompt caching as not retaining data. The response-caching page documents that account-level ZDR separately disables the OpenRouter response cache, while per-request `provider.zdr` does not change response-cache eligibility and therefore does not remove gateway response retention when that cache is enabled. Keep routing, provider-cache, and gateway-cache facts separate; this is a cache-eligibility distinction, not a conflict with ZDR routing enforcement;
- `X-OpenRouter-Cache-Clear` has no effect unless caching is enabled for the request; treat a clear header as an active control request, not evidence that the response-cache plane was enabled. `X-OpenRouter-Cache-TTL` parsing is also evidence-sensitive: out-of-range values clamp, non-numeric values are ignored in favor of the preset/default, trailing non-numeric text is truncated, and decimal values truncate; do not equate a configured string with an effective TTL without the documented response evidence.
- response-cache hits return the stored response verbatim, including when stochastic request parameters such as `temperature` would otherwise vary output; identical body-only outputs can corroborate a response-cache hypothesis but are not proof without cache-status/source evidence.
- no enablement tutorial, TTL-selection advice, cost recommendation, or new cache-plane taxonomy is in scope.

The phrase “`valid` is necessary but not sufficient” is a route-scoped precondition for using an OpenRouter denominator, not a redefinition of the shared Usage Evidence Contract status.

### 4. Route/provider/model attribution

The reference MUST document the current attribution path:

- inspect an already-present `X-OpenRouter-Metadata: enabled` header when a request-level routing snapshot is available; do not add it to production traffic in a passive audit, because changing request logging/metadata shape is outside this change;

- `openrouter_metadata.attempt: 0` with no `endpoints.available[].selected` endpoint indicates that no provider was reached; an absent `openrouter_metadata` field is not proof of a response-cache HIT because it can mean the metadata header was absent, disabled, or invalid, or that the response was a cache hit, a 500 internal-error masking case, an authentication/rate-limit failure, or a pre-router validation failure. The generation API supplies the field but does not define that sign convention. Treat `upstream_inference_cost` as BYOK-only when following the usage-accounting docs; the generation API documents non-null `response_cache_source_id` as the original generation ID when the generation was served from response cache, so use it as historical HIT/source attribution when the generation record is available. The legacy `X-OpenRouter-Experimental-Metadata` header remains accepted, but new diagnostics should use `X-OpenRouter-Metadata`.
