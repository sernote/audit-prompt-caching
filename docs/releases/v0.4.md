# v0.4

v0.4 fixes two ways an audit could give the wrong answer. A timestamp in top-level `instructions` could trigger a high-severity finding on a direct GPT-6.2 Responses request. A Qwen4 Chat response could count the same cache write twice when the provider returned both field names.

### Linter

- **GPT-6.2 Responses (AP-1).** For direct Sol and Astra requests, check the eligible prefix in `input`. Top-level `instructions` follow that input, so a timestamp there no longer triggers the finding, and stable instructions no longer mask a changing input prefix. (#60)
- **Responses TTL and configuration updates.** AP-11 accepts `30m` and `12h` overrides at supported content breakpoints. AP-15 accepts supported `configuration_update.text.format` items on their own or alongside reasoning updates. (#49, #51)
- **Claude Messages (AP-15).** Recognize per-message effort on Fable 5.2, Mythos 5.2 and Haiku 5.5. On Haiku 5.5 with thinking disabled, flag a message-level effort that differs from the request setting. (#56)

### Usage accounting

- Preserve native DashScope input and output totals and their source paths when a response also includes `prompt_tokens_details`. Count matching Qwen4 Chat cache-write aliases once and flag conflicting values. (#50, #58)
- The DeepSeek Messages guide explains which streaming record to collect. Count the final `message_delta.usage` once and flag an incomplete stream if that record is missing. (#57)

### Provider and code audits

- Check Qwen4 cache boundaries and TTL precedence for the API in use. The Kimi Messages guide covers default five-minute writes and reads. The OpenRouter guide distinguishes gateway replay, sticky routing and downstream cache warmth, and includes the 512-token Anthropic tier. (#44, #45, #54, #59)
- Check Azure Standard Responses write charges against the effective TTL and evaluate GPT-6 PTU-M capacity using model-specific weights. Bedrock guidance clarifies the four-write limit and GPT-6 Astra API support. The Claude guide corrects the Haiku 5.5 thinking-history boundary. (#42, #43, #46, #52, #53)
- Follow collection ordering from the producer through inclusion and serialization. Trace usage readers through to the file or network call, and identify any skipped records or uninspected reader. This makes it possible to report a proven code defect while leaving its latency or cost impact unmeasured. (#47, #48, #55)
